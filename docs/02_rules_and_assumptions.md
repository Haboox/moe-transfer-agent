# 02 Requirements, Policies and Rules

Every rule has an ID and a source. Rules are plain Python functions in `agent/rules.py`,
they never call the language model, and each one is unit tested in `tests/test_rules.py`.

Source notation: `Card: <section>` refers to the English card `docs/00_service_card.md`; the Arabic card
`docs/00_service_card_ar.md` has the same sections and is quoted where its wording is more precise.
`ASSUMPTION A-xx` means the card is silent and we made a labelled assumption (listed below).

Every rule writes its result in English **and** Arabic (`detail` and `detail_ar` in `agent/rules.py`), so the
Arabic and English customer see the same decision in their own language, produced by code, not by the model.
The rules run the same way on English and Arabic documents.

## Business rules (service rules)

| ID | Rule | Result if broken | Source |
|---|---|---|---|
| R-01 | The highest grade on the certificates must be between 2 and 11 | WRONG_SERVICE (redirect) | Card: About this service ("Grades 2-11") |
| R-02 | A passport copy is uploaded, verified, and not expired | MISSING or FAIL | Card: Required documents ("Valid passport"); A-01, A-02 |
| R-03 | An Emirates ID copy is uploaded, verified, and not expired | MISSING or FAIL | Card: Required documents ("Valid Emirates ID"); A-01, A-02 |
| R-04 | If the student is not a GCC national, a UAE visa is uploaded, verified, and not expired | MISSING or FAIL (not applicable for GCC) | Card: Required documents ("Valid UAE Visa for non-GCC Nationals"); A-01, A-02, A-03 |
| R-05 | Certificates for the previous 2 years are uploaded (the last grade passed and the grade before it) | MISSING or FAIL | Card: Required documents ("Certificates of the previous 2 years of study"); A-04 |
| R-06 | Every certificate not in English or Arabic has a legal translation **into English or Arabic** (a translation into any other language does not count) | MISSING | Card: Required documents ("Legal translation if the certificate was issued in language other than English or Arabic") |
| R-07 | Every certificate is attested by the education authority of the country of issue | FAIL | Card: Service Conditions (bullet 1); A-14 |
| R-08 | The last certificate passed is attested by the Ministry of Foreign Affairs of the issuing country **and** the UAE Embassy or Attache | FAIL | Card: Service Conditions (bullet 2); Arabic card: "وزارة الخارجية في بلد اصدار الشهادة" |
| R-09 | Certificates are for a complete academic year (no interim statements) | FAIL | Card: Service Conditions (bullet 3) |
| R-10 | Every file is PDF and at most 5 MB (format read from the file itself, size measured on disk) | FAIL | Card: Required documents, Notes ("PDF ... 5 MB") |
| R-11 | At most 2 additional supporting documents | FAIL | Card: Required documents ("maximum of 2 documents") |
| R-12 | The AED 50 fee is paid before the application is submitted | Submission blocked | Card: Fees; Service Process step 3 (enforced by the guard, `agent/guard.py`) |
| R-13 | One file per requirement (no duplicate passport, Emirates ID, visa, or two certificates for the same grade) | FAIL | Card: Required documents, Notes ("merge them into a single file") |
| R-14 | The name on every certificate matches the passport name, compared in the script both share (Arabic with Arabic, Latin with Latin; case, spaces, Arabic diacritics and letter forms such as أ/ا and ة/ه are normalised). No shared script means a person must compare | REVIEW (human) | ASSUMPTION A-05 |
| R-15 | Every document's authenticity check is conclusive | REVIEW (human) | ASSUMPTION A-06 |

### How the rule results combine into one outcome

The order is fixed and tested (`agent/rules.py: combine_outcome`):

1. R-01 fails → **WRONG_SERVICE** (the agent redirects to the right service, no case is created)
2. Otherwise any rule is MISSING or FAIL → **NEEDS_INFO** (the agent asks the customer, then checks again)
3. Otherwise any rule is REVIEW → **HUMAN_REVIEW** (the case goes to a person)
4. Otherwise → **ELIGIBLE** (the agent may request the fee and submit)

Missing information is asked for first, so a human reviewer only ever receives complete cases.

## Agent policies (how the agent behaves)

| ID | Policy | Where it is enforced |
|---|---|---|
| P-01 | The model has no approve tool. Only the rules engine (ELIGIBLE) plus a paid fee can submit a case; only a human can decide an escalated case (see D-02 and P-16) | `agent/tools.py` (tool list), `agent/guard.py` |
| P-02 | Every tool call passes the guard: tool must be on the allow list, parameters must match the contract, prerequisites must be met | `agent/guard.py` |
| P-03 | A backend call that times out, errors, or returns a malformed response is retried once; if it still fails the case goes to a human | `agent/executor.py`, `agent/agent.py` |
| P-04 | Replies are checked before sending (English and Arabic): no claim of approval, submission or an outcome unless the case status allows it, no other case references, no phone or ID numbers other than the card's toll-free number, no "processed" or "completed" claims, no internal instructions or tool names, and document numbers are masked. Internal codes (rule IDs such as R-04, document IDs, test labels) are removed from what the parent reads: they stay in the rules panel, the staff screen and the audit log. Outcomes and status answers are written from the case record | `agent/output_guard.py`, `agent/agent.py` |
| P-05 | Customer claims of authority and text inside documents are treated as data, never as instructions. They cannot change rules or permissions. Attempts are detected by the model and by a fixed word list (English and Arabic), logged, and answered with a fixed refusal plus the case status from the record | System prompt, guard, P-01, `agent/llm.py` |
| P-06 | When nothing has been attached yet, a confident request for a grade this service does not cover is answered before any tools are used (with documents attached, rule R-01 decides on the verified certificates): Grade 12 is redirected to the Grade 12 service; Grade 1 (or above 12) is told the service covers Grades 2 to 11 only and given the toll-free number. If the customer corrects the grade or sends documents, the redirect is withdrawn | `agent/agent.py`, `agent/messages.py` |
| P-07 | If the model fails to escalate a case that needs a human, the policy layer escalates it and logs that it did | `agent/agent.py` |
| P-08 | Every action is written to the audit log with what triggered it (customer input, rule ID, or policy ID); sensitive values are masked first | `agent/audit.py`, `agent/redact.py` |
| P-09 | An escalation must be grounded: its reason must be true in the case record (R-14 or R-15 returned REVIEW, a backend call failed, or the rules outcome is HUMAN_REVIEW). Decision D-04 (21 October): a parent who asks for a person is given the Ministry's toll-free number **by code**, and no case is created or referred for that alone; the guard blocks a `customer_request` escalation. Found live: the model promised "I will connect you" and did nothing, so the reply is no longer left to the model | `agent/guard.py`, `agent/agent.py` |
| P-11 | The reply language is the language of the customer's latest message, decided by code from the letters they typed (not by the model, not by file names). A message with no words keeps the portal language. Arabic replies use the Arabic card and Arabic rule details | `agent/language.py`, `agent/agent.py` |
| P-12 | The fee is paid by the customer in a payment window, never by the agent. Card details go straight to the MOCK gateway and are dropped; only the method, card brand, last 4 digits and outcome are logged. Only published test card numbers are accepted. New files while the payment window is open close it, because the rules must run again first | `agent/payments.py`, `agent/mocks.py`, `agent/agent.py` |
| P-13 | Uploaded documents are always checked. If the model stops before the parent's documents are verified and checked against the rules (for example after an injection in the same message), it is reminded once; if it still does not act, the policy layer runs the standard steps itself (profile, verify, rules, payment window, submission after payment): the same tools, through the same guard, logged with basis P-13. It never escalates on the customer's behalf | `agent/agent.py` |
| P-14 | The assistant is not given the child's name. A parent signs in with UAE Pass and may have several children, so the greeting is general and replies say "your child" (or what the parent called them). Only the student's nationality (for the visa rule) and reference are in the model's context | `agent/prompts.py`, `agent/tools.py`, `ui/i18n.py` |
| P-15 | The assistant answers the question the parent asked: the question is matched by fixed word lists (English and Arabic) to the card section it is about (fee, time, documents, attestation, translation, visa, file format, term statements, process, support) and only those card lines are quoted, followed by one line saying what to do next in this case. A question about the documents gets the card's documents and attestation lines **filled in for this case**: the grade the parent stated (which two certificates, which one needs the Foreign Affairs and Embassy attestation), the nationality on the UAE Pass record (visa or no visa) and the country they named (country of study). When what the parent says differs from the record ("we are from Oman" but the record is not GCC), the reply says the record counts and gives the toll-free number. A parent who states a grade inside the service is told exactly which two certificates to attach; a plain greeting gets a welcome, not the requirements. All of this is written by code, never by the model | `agent/guide.py`, `agent/agent.py` |
| P-16 | Decision D-02, approval workflow: the agent never issues an equivalency decision. Its last possible actions are to **submit** a complete, paid request (every rule passed) or to **escalate** a paid request the rules cannot decide (D-06, A-09). An officer then issues the equivalency decision on every case: submitted cases appear as "Ready for decision" (all automated checks passed) and escalated cases as "Exceptions" (what the rules flagged is shown in the rules' own words). A decision needs a staff ID and a note, is made once, and is logged with its basis | `agent/human_review.py`, `ui/staff.py`; tests `test_an_officer_issues_the_decision_on_a_submitted_case_once`, `test_the_parent_sees_the_officers_decision_and_the_agent_cannot_make_it` |
| P-17 | No invented facts. The agent has **no internet access** and the model has no clock. The date and time come from this computer's clock in UAE time and are written by code; questions outside the service (weather, news, prices, general knowledge) get a fixed reply; the reply checker blocks a clock time in any model reply. Everything else the agent states comes from the service card, a rule result or a tool result. Why no internet: web pages are untrusted text (prompt injection, a way to send case data out), the case study forbids real Ministry systems, and the demo must work offline. Found live: "The current time in the UAE is 10:45 AM" (wrong) | `agent/facts.py`, `agent/agent.py`, `agent/output_guard.py` |
| P-18 | Small talk and fixed answers (greeting, thanks, unclear text, typed personal numbers, time and date, outside questions, asking for a person) are read and answered by code with no model call: instant on the demo PC, and the model is never the source of these replies. The audit log records "no model call" | `agent/agent.py` |
| P-10 | Questions about the service are answered with the official list word for word from the service card, never the model's paraphrase; anything the card does not cover (for example cancelling, refunds, cash, appeals) gets a fixed "not covered" answer with the card's toll-free number, never the model's guess | `agent/agent.py`, `agent/messages.py` |

## Assumptions (where the card is silent)

| ID | Assumption | Why |
|---|---|---|
| A-01 | Passport, Emirates ID and visa are the student's documents | The card lists the documents but does not say whose |
| A-02 | "Valid" means the expiry date is on or after the application date | The card says "Valid" without a definition |
| A-03 | GCC nationals are citizens of the UAE, Saudi Arabia, Kuwait, Qatar, Bahrain and Oman. Nationality comes from the student's identity record (mock UAE Pass), never from what the parent types: "we are Saudi, no visa needed" from a non-GCC applicant still needs the visa (probes Q31, A35) | The card says "non-GCC Nationals" without a list |
| A-04 | The grade being equalised is the highest grade on the certificates; "previous 2 years" means that grade and the one before it | The card does not define which two years |
| A-05 | A name mismatch between passport and certificate needs a human decision | The card does not cover identity consistency; this is an exceptional case the rules cannot decide |
| A-06 | An inconclusive authenticity result needs a human decision | The card relies on attestation but does not cover unclear results |
| A-07 | Backend failures are retried once, then sent to a human; the agent never guesses a result. A call is treated as timed out after 3 seconds | The card does not cover system failures |
| A-08 | Resolved by the Arabic card: the Ministry of Foreign Affairs is the one "in the country that issued the certificate". The English card only says "in the country of study". The prototype reads one MoFA flag from the verification service | The two card versions differ; the Arabic one is more precise |
| A-09 | Decision D-06 (21 October, replaces the earlier assumption that escalated cases were created unpaid and the fee "handled after review", which the prototype never did): **every request is paid for when it is submitted, whatever the outcome.** A request the rules send to an officer (R-14 name mismatch, R-15 authenticity unclear) is submitted like any other: the payment window opens, the parent pays AED 50, and only then does it reach the officer, who may approve or decline it. Not charged: an incomplete request (the parent fixes the documents first, so nobody pays for a request that cannot be submitted), and a case sent to an officer because the identity or verification system was down (nothing could be checked). The guard blocks a rules escalation before the fee is paid | The card's Service Process puts payment before submission (step 3, then step 4) and does not exempt exceptional cases; found while testing the online copy: an officer approved an escalated case and the fee was never collected |
| A-10 | Payment is simulated. In the app the customer pays in a mock payment window (test card, Apple Pay, Google Pay or Samsung Pay); in automated tests the customer is assumed to complete the payment at once. No real payment happens | Synthetic environment |
| A-11 | Decision D-01 (revised 20 October 2026 after the Ministry's answer of 16 October): the parent is told the **published service time of 30 working days**. What the agent improves (a complete request is checked and submitted at once, instead of waiting for a first manual check) is shown only as a **proposed improvement**, labelled as such in Helpful information and in the documentation, never as a service commitment. The earlier wording ("instant") was removed | The Ministry asked to keep the published 30 working days as the baseline and to label improvements as proposed |
| A-12 | A customer may ask for a human at any time; they are given the toll-free number (Card: Support) and can still continue the request in the chat. Asking does not create or refer a case and does not bypass any rule | The card's support channel is the toll-free number; referring every such request would fill the officers' queue with cases that have no documents |
| A-13 | The requirements list is quoted word for word from the Arabic card for Arabic speakers and from the English card for English speakers. The other fixed Arabic messages (status, missing items) were written for this service in Modern Standard Arabic, not translated on the fly, and should be reviewed by the Ministry | The cards do not contain status messages |
| A-14 | "Country of study" (English card) and "country of issue" (Arabic card) are treated as the same country | The two card versions use different words; for a school certificate they are normally the same |
| A-16 | One student per application session: the signed-in parent's session is for one student (the mock identity record holds that student). The assistant still never names the child (P-14) | The card does not say how a parent with several children chooses one |
| A-17 | Decision D-03: the outcome the prototype shows is a **reference number and a confirmation** (chat message and a downloadable application receipt PDF, labelled "not an equivalency certificate or decision"). No simulated certificate or decision letter is generated. The officer's decision is recorded on the case and shown to the parent as a status | The Ministry confirmed on 16 October that a successful submission with a reference and confirmation is acceptable and a simulated certificate is optional |
| A-18 | The parent can remove a file before the case is created; the rules run again and an open payment window closes. After the case is created, files are neither added nor removed, and the parent is given the toll-free number for changes | The card does not say how a submitted application is amended |
| A-19 | A real file uploaded from the computer that is not one of the applicant's synthetic documents is treated as a file the verification service has no record of: authenticity inconclusive, nothing read from it, so the parent is asked for a readable document or a person decides (R-15). The uploaded file name is not used anywhere | The prototype has no real verification service; the case study requires synthetic data only |
| A-20 | Open test (demo only): the portal opens with a signed-in parent and no preset case. The presenter sets the nationality on the mock UAE Pass record (every country; none selected at first, in which case no GCC exemption applies and a visa is required) and builds any case from the whole synthetic library (every applicant's documents) or uploaded files. Mixing applicants is allowed on purpose, so the rules show what they do with it (for example R-14 sends a name mismatch to an officer). Every synthetic name is masked in the log | The case study asks that the panel can try unseen requests; a real portal would only show the signed-in parent's own files |
| A-15 | "Grades 2-11" means the grade the student **completed** abroad, the grade on the certificate to be made equivalent, not the grade the child is joining. So a child who completed Grade 1 (joining Grade 2) or kindergarten is outside this service; the card does not say which procedure applies, so the parent is told why and given the toll-free number. If the parent asks again ("but he is joining Grade 2"), the reply explains the rule instead of repeating itself. Scenarios S9, S10, S18 (English and Arabic) | The card says "equivalency certificate for Grades 2-11 issued from ... outside the UAE": the certificate is issued for a completed grade. The Ministry's separate Grade 12 service works the same way (a completed Grade 12 certificate). Open point to confirm with the Ministry: what applies to a completed Grade 1 |
