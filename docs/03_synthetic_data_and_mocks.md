# 03 Synthetic Data and Mock Integrations

> The service is real; everything the agent touches is not. Every person, document, number, school
> and stamp below is invented and labelled SYNTHETIC or MOCK. No real Ministry system is called.

## 1. Synthetic records and documents

Generated by `scripts/generate_synthetic_data.py` (reproducible: same output every run).

| Output | What it is |
|---|---|
| `data/synthetic/personas.json` | 15 mock UAE Pass accounts (parent + student), with English and Arabic names and stories |
| `data/synthetic/documents.json` | 158 document records: what the mock verification service "knows" about each file |
| `data/synthetic/documents/<persona>/en/*.pdf` | English edition: the documents in English (an Arabic or French original is shown with English labels) |
| `data/synthetic/documents/<persona>/ar/*.pdf` | Arabic edition: the same documents in Arabic (see below) |

Every PDF is watermarked "SYNTHETIC SAMPLE - NOT A REAL DOCUMENT"; Arabic edition PDFs also carry
"عينة اصطناعية". Arabic text is drawn with proper letter joining and right to left order
(`arabic-reshaper`, `python-bidi`) in an open-licence font bundled in `assets/fonts`.

### Two editions: English and Arabic, one set of facts

The portal shows the edition that matches its language, so every scenario can be shown in either language
with the same expected outcome. Each applicant's facts are written once in the generator and shared by both
editions: **the same school, country, grades, academic years, issue dates, subjects, marks, attesting bodies and
missing stamps**. Only the language of the documents changes (checked by
`test_both_document_editions_describe_the_same_student_and_school`). In the Arabic edition:

* certificates and their stamps are in Arabic (school, grade name, subjects, dates with Arabic month names);
* identity documents carry the name in Arabic and Latin script, as UAE documents do;
* French originals (Belgium, France) stay French, with **legal translations into Arabic** instead of English: the
  card accepts a certificate in English or Arabic, or a legal translation, so this proves both directions work;
* the Omani student's Grade 4 certificate shows the full lineage name in both editions ("Salem bin Saeed Al
  Qarwani" / "سالم بن سعيد القرواني") while the passport says "Salem Al Qarwani" / "سالم القرواني": a real naming
  difference only a person can judge (R-14 REVIEW);
* the Filipino student's injection text is in Arabic inside the Arabic certificate.

The two editions use the same document numbers for the same person, so uploading the same certificate from both
editions is caught as a duplicate (R-13).

### How the data is labelled so it can never pass as real

* Every record carries `"label": "SYNTHETIC DATA - FOR PROTOTYPE ONLY - NOT A REAL PERSON OR DOCUMENT"`.
* Every identifier starts with `MOCK-` or `SYN-` (e.g. `MOCK-P-IND-4801371`, `MOCK-EID-0001-01`, `SYN-STU-P01`).
  No real Emirates ID format numbers are used.
* Every PDF has a red banner, a diagonal watermark, and "SYNTHETIC STAMP" on every attestation.
* Every school name ends with "(SYNTHETIC)". People's names are fictional: invented surnames that belong to no real person.
* Tests check all of the above (`tests/test_tools_and_mocks.py`, `tests/test_data_and_interpret.py`).

The people are invented, but the context around them follows public information, so the cases look and behave like real applications.

## 2. Mock integrations (each mocked system is a tool with a defined contract)

All mocks live in `agent/mocks.py`; their contracts are Pydantic models in `agent/models.py`.
A response that does not match its contract is treated as **malformed** and is never trusted.

| Mock system | Real system it stands in for | Tool(s) the agent calls | Input contract | Output contract |
|---|---|---|---|---|
| MOCK Identity | UAE PASS / identity authority | `get_applicant_profile` | none (session identity) | `ApplicantProfile` (uae_pass_ref, student ref, names, nationality) |
| MOCK Document Verification | Attestation and authenticity checks | `verify_documents` | optional `doc_ids` (must be this session's uploads) | `VerificationResult` per document (authenticity, expiry, grade, language, complete year, attestation flags and authority names, untrusted document text) |
| MOCK Payment Gateway | MoE e-payment | `request_payment` (opens the payment window), then the parent pays in the window | none (amount fixed at AED 50 from the card; the model cannot set it) | `PaymentRequest` (payment_id, PENDING), then `PaymentReceipt` (receipt_id, amount, PAID, method, last 4 digits only) |
| MOCK Case Management | MoE case system | `submit_application`, `escalate_to_human`, `get_case_status` | `escalate_to_human`: `reason_code` from a fixed list, short summary | `CaseRecord` (SYN-xxxx reference, status) |
| Service card lookup | The published service card | `get_service_requirements` | none | Requirements text with rule IDs |

### Realistic timeouts, errors and malformed responses

| Behaviour | How it is simulated | How the agent handles it |
|---|---|---|
| Normal latency | Each call waits `MOCK_LATENCY_SECONDS` (0.3 s) | |
| Timeout | The system hangs for `MOCK_HANG_SECONDS` (6 s); the executor stops waiting after `TOOL_TIMEOUT_SECONDS` (3 s) | Retry once; if it fails again, mark the document unverified and escalate (P-03) |
| Server error | Raises an HTTP 503 style error | Same retry policy |
| Malformed response | Returns wrong types and unexpected fields (e.g. `"authenticity": 42`) | Rejected by the contract, same retry policy; never used |
| Wrong applicant's document | Returns "not found" | Blocked earlier by the guard (only own uploads) |

Failures are switched on per system for tests and demos, for example `{"verification": ["timeout"]}`
(first call times out, then works) or `{"verification": "malformed_always"}`. In the app this is
the **Simulate a verification system problem** option under **Demo controls**.

### The mock payment window

In the app the parent pays in a payment window (card, Apple Pay, Google Pay or Samsung Pay, all simulated).
The card form checks the number (Luhn checksum), the expiry date and the CVV, and accepts **only published test
card numbers**, so a real card can never be charged even by mistake:

| Test card | Result |
|---|---|
| 4242 4242 4242 4242 | Approved (Visa) |
| 5555 5555 5555 4444 | Approved (Mastercard) |
| 4000 0000 0000 0002 | Declined by the bank |
| 4000 0000 0000 9995 | Declined: insufficient funds |
| Any other number | Refused: "only test cards" |

The card number, expiry and CVV go straight to the mock gateway and are dropped there. The agent, the model and
the audit log only see the method, card brand, last 4 digits and the outcome (policy P-12). In automated tests and
scenario runs the parent is assumed to complete the payment at once (assumption A-10).

### File checks are real

When a customer uploads a file, its format is read from the file's first bytes (`%PDF-`) and its size is
measured on disk (`MockBackend.file_info`). Rule R-10 (PDF, 5 MB maximum) runs on those measured values.

## Open test (no preset case)

`agent/mocks.py` adds one more signed-in parent at run time, `SYN-OPEN`, with no documents of its own. Its document
list is the whole synthetic library (all 15 applicants, in the page language's edition) plus files uploaded in the
session; the nationality on its mock UAE Pass record is chosen in Demo controls. It is used to build unseen cases
live (assumption A-20). It is not written to `personas.json`, so the prepared data stays as generated.
